# Fleet Manager architecture (APP V1 / Phase 4)

`app/data` is the personal development data root and is never committed. Packaged Electron applications must use `app.getPath('userData')/fleet-manager-data` instead: an asar application path is not a writable data directory. The root should remain an injected/owned service dependency, not be hard-coded in repository code. `fleetSimulation/map` remains an Optimizer workspace and is populated only when the user explicitly imports or starts a saved task.

The Renderer has no Node.js integration. Its only privileged boundary is `window.fleetManager`, supplied by the context-isolated preload script. Main owns JSON validation, atomic writes, staging and process spawning.

Optimizer-wide settings deliberately remain outside Manager's per-user Galaxy/Node store. Main reads and atomically writes the existing `fleetSimulation/poc/optimizer_v2_daily.json`; `run_optimizer.bat` already stages that exact file into the isolated Godot project for every single or queued run. Saves preserve unknown JSON fields, existing indentation/newline style, and skip the write entirely when the parsed value is unchanged. This keeps one runtime source of truth while preserving the `app/data` versus `fleetSimulation/map` boundary.

`OptimizerRunner` holds a process-wide lock, streams stdout/stderr, writes a runtime task snapshot with selection and Node/Common SHA-256 hashes, requires exit code zero, rejects unchanged content or malformed result files, and validates Galaxy/Node where the Result exposes resolver identity. Existing Results do not embed Manager configuration hashes, so this cannot prove cryptographic result-to-input ownership; it reliably rejects stale, unchanged and obviously mismatched results without changing the Optimizer.

Phase 2 keeps management metadata separate from Optimizer JSON. Node `meta.json` owns stable Version IDs, display names and the default ID; Common uses the same pattern. Renaming changes only display metadata. Every Version/Common is a separate JSON file, and all writes use temporary-file replacement. Templates live under `data/templates`, are created only by explicit user action, and contain an ordinary validated Node JSON snapshot.

Node creation accepts either a selected Node Version or a managed template. It preserves the source configuration and rewrites only `galaxy` and `node` before schema validation and atomic creation. New Version/Common actions initialize from the corresponding default configuration; Copy actions initialize from the current selection. Neither searching nor applying a result creates management objects.

Best Found application is a Main-process transaction: stage the selected Manager Node/Common, invoke the existing `run_optimizer.bat <galaxy> <node> --c`, require exit code zero, parse and validate the modified workspace Node including identity, then atomically replace only the selected Manager Version. A non-zero copy exit or invalid workspace JSON exits before the Manager write. The Renderer enables this action only for a successful search result tied to the current four-part selection.

Galaxy rerun selection is resolved in Main from Manager metadata: every Node contributes exactly its default Version and the Galaxy contributes exactly its default Common. `OptimizerRunner.runQueue` acquires the same process-wide lock used by single search and Best Found copy, retains it for the complete batch, and invokes the existing per-Node staging/result-validation path serially. A Node failure is converted into a batch item failure and the next Node continues; missing `best_result` or `verified_baseline` is also a failure, so stale data cannot be presented as the current item result.

Configuration change detection compares the Optimizer-standardized `formation_key` when both candidates provide it. Real Result fixtures confirm that the key includes Formation and Loadout. For compatible older Results without keys, the shared structural diff compares position, ship, Primary, Secondary and Tertiary fields. Fleet-resource-only changes are ignored. Completed batch data remains transient Renderer state: rerun never invokes copy mode and has no Manager write path. Users open an individual changed Node and explicitly use the existing Best Found flow if they choose to adopt it.

The Renderer has two bridge implementations behind the same `FleetManagerApi` contract. Electron exposes the authoritative filesystem and Optimizer implementation through preload. A standard browser falls back to a web runtime that persists its workspace in `localStorage`, so the UI can be built and deployed without Electron-specific globals. The web runtime intentionally does not reimplement the Optimizer: its search results are deterministic workflow fixtures until a controlled local service or server executor is connected. Dialogs are application-owned rather than `window.prompt` / `window.confirm`, keeping CRUD and destructive confirmations functional in Electron, the in-app browser and future web deployments.

Formation selectors are normalized only at the UI boundary. Numeric values `1..5`, numeric strings and canonical English ship identifiers all resolve to the same display option. Edits preserve the existing representation for each slot (number stays number, numeric string stays numeric string, canonical string stays canonical string), preventing read/save-only format drift while keeping Optimizer JSON legal.

Loadout selectors use `allowed_mod_slots` as ordered data, not booleans. A value of `0` maps to `null`; positive numeric values index the configured array, while string configurations keep internal Mod IDs. The UI chooses a toggle only when the current array contains `null` and exactly one concrete Mod, otherwise it uses a select or an unavailable state. Standard-Galaxy Tertiary Mods remain automatic in the recovered Fleet scope logic and are not presented as manually selectable search slots.
