# Fleet Manager architecture (APP V1 / Phase 4)

V1.2 adds an in-memory Main search queue with immutable per-item snapshots, serial execution, individual logs/results, and Windows process-tree cancellation. `GalaxyRerunService` accepts an ordered subset of default-version Nodes and one Search draft, then uses the same Runner lock and stop methods. `taskkill /T /F` terminates the active BAT tree; waiting queue items and unstarted rerun Nodes become canceled. Queue history is session-only. The Renderer persists page contexts separately in `localStorage` and shows summarized Chinese errors with expandable raw details. Node parsing canonicalizes ship-key aliases and rejects conflicting duplicate values.

`app/data` is the personal development data root and is never committed. Packaged Electron applications must use `app.getPath('userData')/fleet-manager-data` instead: an asar application path is not a writable data directory. The root should remain an injected/owned service dependency, not be hard-coded in repository code. `fleetSimulation/map` remains an Optimizer workspace and is populated only when the user explicitly imports or starts a saved task.

The Renderer has no Node.js integration. Its only privileged boundary is `window.fleetManager`, supplied by the context-isolated preload script. Main owns JSON validation, atomic writes, staging and process spawning.

Search preferences and Optimizer-wide settings remain outside Manager's per-Node store. Both resolve one effective file with local-first fallback: `fleetSimulation/map/search_config.json` over `poc/search_config.json`, and `map/optimizer_v2_daily.json` over `poc/optimizer_v2_daily.json`. `poc` is the committed default; Manager writes only ignored `map` overrides. Optimizer saves preserve unknown fields and source formatting, while BAT uses the same local-first Optimizer selection.

`OptimizerRunner` holds a process-wide execution lock, streams stdout/stderr, and creates an immutable single-search snapshot before staging. Start first atomically saves and reloads the Search draft; failure aborts the run. The confirmed Search is recorded in the snapshot and overlaid onto the staged Node without mutating its saved Version. The snapshot owns Task ID, Galaxy, Node, Version/Common IDs and names, persisted and staged Node hashes, Common/Optimizer hashes, environment, Search parameters and start time. Result output, logs and Best Found remain associated with this snapshot instead of the Renderer’s current page selection. Result acceptance still requires exit code zero, changed result content, valid JSON and matching Galaxy/Node identity where exposed.

The execution lock prevents a second single-node search, a Galaxy rerun, or Best Found copy while a search runs. It is not a global application lock. Main rejects writes only to the exact task Node+Version, the task Galaxy+Common, and Optimizer Public; unrelated Node Versions and other Galaxy Commons remain writable. Renderer mirrors these rules with an explanatory read-only notice, while Main remains authoritative.

Phase 2 keeps management metadata separate from Optimizer JSON. Node `meta.json` owns stable Version IDs, display names and the default ID; Common uses the same pattern. Renaming changes only display metadata. Every Version/Common is a separate JSON file, and all writes use temporary-file replacement. Templates live under `data/templates`, are created only by explicit user action, and contain an ordinary validated Node JSON snapshot.

Node creation accepts either a selected Node Version or a managed template. It preserves the source configuration and rewrites only `galaxy` and `node` before schema validation and atomic creation. New Version/Common actions initialize from the corresponding default configuration; Copy actions initialize from the current selection. Neither searching nor applying a result creates management objects.

Best Found application is a Main-process transaction bound to a completed Task ID, never the current page selection. Before copy, Main verifies that the task succeeded, its Result is still the latest for that Node, and the target Version hash still equals the snapshot hash. It then stages the task source Manager Node/Common, invokes `run_optimizer.bat <galaxy> <node> --c`, validates the modified workspace Node including identity, and atomically replaces only that task Version. A changed target hash, non-zero copy exit, or invalid workspace JSON exits before the Manager write.

Renderer state is split into independent page contexts (`node`, `search`, `templates`, `common`, rerun Galaxy), per-domain drafts, and a transient task queue (`waiting`, `running`, `success`, `failed`, `canceled`). Node, Search, Galaxy Common and Optimizer Public drafts do not impose cross-domain navigation locks. Search is an independent low-frequency draft and persists automatically when a search or rerun starts. Dirty drafts remain in memory across page/context changes; only an operation that would discard data or application close requires confirmation.

Galaxy rerun selection is resolved in Main from Manager metadata: each selected Node contributes its default Version in the user's chosen order and the Galaxy contributes its default Common. The batch saves and freezes the Search draft once, then records it in every task snapshot and staged Node. `OptimizerRunner.runQueue` acquires the same process-wide lock used by single search and Best Found copy, retains it for the complete batch, and invokes the existing per-Node staging/result-validation path serially. A Node failure is converted into a batch item failure and the next Node continues; missing `best_result` or `verified_baseline` is also a failure, so stale data cannot be presented as the current item result.

Galaxy rerun change detection first compares the integer parts of Baseline and Best Found Used FR, using `Math.floor` on each value. When either Used FR is unavailable, it compares the Optimizer-standardized `formation_key` if both candidates provide it; compatible older Results fall back to a structural diff of position, ship, Primary, Secondary and Tertiary fields. Rerun itself does not invoke copy mode or update Manager Versions. After the batch, users may explicitly apply an individual changed Node or apply all eligible changed Nodes in sequence; each application uses the same Task ID, Result, Version-hash and copy validation path.

The Renderer has two bridge implementations behind the same `FleetManagerApi` contract. Electron exposes the authoritative filesystem and Optimizer implementation through preload. A standard browser falls back to a web runtime that persists its workspace in `localStorage`, so the UI can be built and deployed without Electron-specific globals. The web runtime intentionally does not reimplement the Optimizer: its search results are deterministic workflow fixtures until a controlled local service or server executor is connected. Dialogs are application-owned rather than `window.prompt` / `window.confirm`, keeping CRUD and destructive confirmations functional in Electron, the in-app browser and future web deployments.

Formation selectors are normalized only at the UI boundary. Numeric values `1..5`, numeric strings and canonical English ship identifiers all resolve to the same display option. Edits preserve the existing representation for each slot (number stays number, numeric string stays numeric string, canonical string stays canonical string), preventing read/save-only format drift while keeping Optimizer JSON legal.

Loadout selectors use `allowed_mod_slots` as ordered data, not booleans. A value of `0` maps to `null`; positive numeric values index the configured array, while string configurations keep internal Mod IDs. The UI chooses a toggle only when the current array contains `null` and exactly one concrete Mod, otherwise it uses a select or an unavailable state. Standard-Galaxy Tertiary Mods remain automatic in the recovered Fleet scope logic and are not presented as manually selectable search slots.
